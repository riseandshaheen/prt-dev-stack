# PRT dev stack: P0 break-test run

Oct 1, 2026 · sling `v3.0.0-alpha.5`, reference node `test-contracts-bump`, echo app `0x6c2E…6146` · harness in [`harness/`](../README.md)

## Summary

Every P0 scenario from the [test design](../../test-design-claude.md) ran against the live stack, plus a golden run and T3 split in two. Safety held in every run: no node staged, accepted or built on a wrong state, and no bond went to the wrong party.

Two issues concern liveness and detection rather than safety:

1. **One offline tournament halts the app for good (R5b).** If sling is down while a sybil disputes, the rival commitment wins, both nodes refuse to stage it, and the epoch never settles. This happens even when the rival's final state is the correct one.
2. **Neither node detects a chain reset (T3).** Both treat it as lag and then loop on errors, and the reference node keeps reporting the app as `OK` while serving the old history.

## Issues

### 1. A rival that wins while sling is down halts the app (medium)

R5b: sling was paused through epoch 34's tournament, and a dave sybil joined against the Go node's commitment. The Go node does not advance matches or claim timeouts, so the sybil won at block 15318.

- The Go node flagged the app **DIVERGED** 20 blocks later: "Epoch 34 has inconsistent commitment between off-chain (0x4584…) and on-chain (0x5da0…)". This is a correct, early halt.
- Sling, once resumed, logs "local commitment lost dispute tournament for epoch 34" every tick, sends nothing, and starts computing epoch 35 locally.
- No one stages. After 1,400 more blocks epoch 34 is still unstaged, so the app never settles again.

The R5b run expected the rival's state to be accepted after the staging period and timed out waiting, so it is recorded as failed. The scenario now checks for this halt instead, but that version has not been rerun.

The sybil's commitment ends on the **same final state** as the honest one (`0x1fdeada2…`). Dave's `patched_commitment` lies at an intermediate leaf. Staging the rival's result would have produced the correct machine state, but the Go node halts on the commitment mismatch alone.

Why it matters: the Go node never defends, so the app's safety rests on sling alone. If sling is offline for one join window (about 300 blocks), an attacker with one bond can freeze the app. Questions for the teams:

- Should the Go node play matches, or at least claim timeouts, when it holds the honest commitment?
- When a rival wins with the same final state, should an honest node stage it rather than halt?
- A rival with a *wrong* final state was not tested; that is the next variant to run.

### 2. Neither node detects a chain reset (medium)

T3: Anvil restarted from its dump (block 25) while both nodes kept their state (sling at block 17724, reference at 17529).

- Below their saved height, both treat the reset as lag. The Go node logs "most recent block is lower than the last processed one"; sling logs "tournament event watermark 17724 is ahead of finalized head". The app stays `OK`.
- Past their saved height (T3b), both loop on errors. The Go node logs "failed to fetch inputs for epoch 37" and "no contract code at given address" for epoch 35's tournament; sling logs "dispute planning failed, retrying next tick". The Go node still reports `OK`, and its JSON-RPC serves the old 38-epoch history as current.
- Nothing is sent, so nothing unsafe happens. But epoch 0's tournament on the new chain ends with no winner, so the app can never settle and nothing says so.

Suggestion: on start, and when the head goes backwards, compare a stored block hash with the chain, and on mismatch mark the app failed.

### 3. The stage race depends on timing (info)

In one run, sling and the Go node both sent `stageTournamentResult` into the same block. The Go node won and sling's reverted. In the rerun, sling sent its sentry claim in that phase instead, and the Go node staged alone. Both are correct behaviour. The loser's revert reason was not captured in the first run (a harness bug since fixed), so `TournamentResultAlreadyStaged` handling is confirmed by the rule, not by observation.

### 4. `BlockOutOfRangeError` on historical reads (low, unconfirmed)

The Go node's evm-reader failed 3 times in R4, for example: "failed to get current sealed epoch at block 5277: BlockOutOfRangeError: block height is 5288 but requested was 5277". The requested block exists. It happened only while the harness mined 10 blocks per call, and the node recovered on the next tick. A plain Anvil with `--preserve-historical-states` answered historical reads after a batch mine, so the cause (Anvil or the reader) is still open.

### 5. Disk use (operational)

Sling's snapshots reached 1.09 GB after 35 echo epochs. The sybil image adds 5.2 GB plus an 11 GB build cache. During this run the Mac's disk filled, Docker went read-only, and the stack needed a restart. Postgres recovered from its WAL and sling's database passed an integrity check. Keep at least 20 GB free before running R5 or R5b.

## Bugs fixed during the run

These were in the tooling, not the nodes:

- **Visualiser**: compared the reference node's provisional values for an open epoch (bounds and hash of the inputs processed so far), which showed a false "disagree" around every epoch change.
- **Visualiser**: marked a sybil commitment "honest" because its final state matched; the root now decides.
- **Harness**: revert reasons came from replaying at the previous block, which misses an earlier transaction in the same block; they now come from a trace of the transaction.
- **Harness**: C4 and R4 windows, R5 finish detection, sybil account numbering (dave counts accounts from 1), and long mines timing out.
- **Stack**: dave's `test/Dockerfile` needs `--build-arg DAVE_EMULATOR_GITLINK=…` when built outside a checkout with the submodule index; without it the build fails at `build-programs`.
